# Scope

BudsDesk is a native desktop app that controls OPPO / OnePlus / realme TWS earbuds over their own
vendor Bluetooth control channel. It is an interoperability project: it speaks a documented-by-
measurement wire protocol to hardware the user already owns and has already paired.

This file is the Phase 0 deliverable. It is the boundary of the project. Anything not written
here is not in scope, and anything written here as out of scope stays out of scope.

---

## 1. Area of interoperability

The earbuds in this family expose a vendor RFCOMM (SPP) service named `enco link`, with the
SDP service UUID `0000079a-d102-11e1-9b23-00025b00a5a5`. Over that one serial channel the
companion phone app reads and writes device state: battery, wear, noise control, equalizer,
gestures, multi-connect, firmware string, codec.

BudsDesk speaks **that channel**. It does not touch the standard Bluetooth profiles the same
earbuds also expose (`HFP`/`A2DP`/`AVRCP`), which macOS already drives by itself for audio.

Interoperability means: the bytes this app sends are the bytes the official app sends; the bytes
it understands are bytes the hardware actually sent. Where the two disagree, the hardware wins.

## 2. Devices in scope

**Target family:** TWS earbuds from OPPO, OnePlus and realme (realme is an OPPO sub-brand and
shares the protocol stack) whose SDP records advertise the `enco link` service above, and
which expose the vendor control channel on an RFCOMM channel resolved at runtime from SDP.

**Feature coverage per device is data, not code.** Every model's capabilities live in
`devices/<vendor>-<model>.json` (see `devices/README.md`). One binary drives every model; a model
whose capability file marks a feature `unconfirmed` gets no write path for it, and a model with no
capability file at all still connects and shows what it can read.

**Confidence is per model, per feature.** The registry records `measured`, `inferred` or
`unconfirmed` for each capability. `unconfirmed` means no write path exists in the UI, by
construction.

**Verified on real hardware so far:**

| Model | Firmware string as reported | Status |
|---|---|---|
| OnePlus Buds 4 | `1,2,138,2,2,138,3,1,01,3,2,105` | Measured; see `capture/` |

Everything else in `devices/` is marked `unconfirmed` until someone runs the hardware loop
(`Tools/hardware-loop.md`) against that model and commits the log.

## 3. Hosts in scope

- **macOS (first ship target):** IOBluetooth RFCOMM, Apple silicon, macOS 26+.
- **Later, on the same protocol core:** Windows (`Windows.Devices.Bluetooth.Rfcomm`) and Linux
  (BlueZ RFCOMM sockets). The protocol core is Foundation-only and transport-agnostic precisely
  so these can be added without touching a decoder.

**Out of scope as hosts, permanently:** iOS (a third-party app cannot open the vendor RFCOMM
service without MFi or a different transport) and Android (the reference app already exists and
is the better tool there).

## 4. Out of scope

These are not "not yet". They are never.

- **Firmware OTA. Permanently, without exception.** Firmware updates travel on a separate
  service — BESOTA, RFCOMM channel 13 — and are the one part of this device that can leave the
  hardware unusable if written wrongly. BudsDesk does not open channel 13 for any reason: not
  for discovery, not for testing, not "just to see what it says". There is no OTA UI, no OTA
  code path, and no OTA decoder in this repository.
- **Fuzzing and probing by enumeration.** Only command ids observed in a committed capture may
  be sent, and only setters observed being used in a capture may be sent by a write path. No
  sweeping `0x00…0xFF`, no "probably this one". An id received but never seen before is logged
  and dropped, never answered. The one deliberate exception is the capability *getter* sweep that
  a hardware-loop run performs under a committed, reviewed list — and it is read-only.
- **Accounts, cloud, telemetry, analytics, crash uploads, update checks.** The app talks to the
  earbuds and nothing else. There is no networking code in the project.
- **Server-driven behaviour.** The phone app's feature list can be server-controlled per model
  and region. BudsDesk has no server, so a feature that only exists server-side simply does not
  exist here; the registry records it as `unconfirmed` rather than guessing.
- **Copying the reference app.** No decompiled code, no extracted assets, no fonts, no icons, no
  bundled JSON lifted out of the APK. The APK is read to answer questions; nothing is shipped
  from it. Every visual in BudsDesk is generated by code in this repository.
- **Volume-key injection and system-volume control.** This app does not synthesize media key
  events or change macOS output volume. Where the hardware has its own volume control, the app
  reads and writes the hardware's own setting only.
- **Prompt-voice pack upload.** The vendor setter for a prompt voice is a file transfer. It is
  treated as firmware-adjacent and is out of scope.
- **Modifying the device's flash state outside the measured setter allowlist.** Anything that
  writes state the captures have not already shown being written requires an explicit yes from
  the user first, per Non-negotiable 10.

## 5. Platform requirements

- macOS 26 or later, Apple silicon.
- The earbuds paired in System Settings → Bluetooth. BudsDesk finds them by the control service
  they advertise, not by name and not by a hardcoded address.
- Bluetooth permission (TCC) granted to the app bundle. A process without it sees an empty
  paired-device list rather than an error — that is a permission problem, not a discovery bug.
- **Only one process may hold the control channel.** BudsDesk and the vendor phone app cannot
  both drive the earbuds at once, and neither can BudsDesk and another copy of BudsDesk.

## 6. Legal posture

- This is **interoperability reverse engineering of software and hardware the author lawfully
  possesses**. The goal is to let the owner of a device use it from a computer they own.
- **No circumvention of protection measures.** The control channel is an unauthenticated vendor
  serial protocol; nothing encrypted, signed or access-controlled is bypassed. No key schedules
  are defeated, no DRM is touched, no attestation is fooled.
- **No redistribution of the original binaries or assets.** The APK, its decompiled output, its
  resources and its assets are used for study and are never committed to this repository or
  shipped in a release.
- **No claim of affiliation.** BudsDesk is not made by, endorsed by, or affiliated with OPPO,
  OnePlus, realme, or HeyMelody's publisher. Product names appear only as factual device names,
  because naming the device you support is not a claim of endorsement.
- **Writes are user-initiated and reversible.** The app's setter surface is limited to settings
  the user can change back by hand, on the device or in the app. The one irreversibly destructive
  area (firmware OTA) is excluded entirely, per §4.
- **No warranty accepted on behalf of the user's hardware.** The app's README states plainly
  which writes have been verified on hardware and which have not.

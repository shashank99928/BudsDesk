Which earbuds BudsDesk works with

One model is measured end to end. The rest of the family is expected to connect and read, and none of it is writable yet. This page explains exactly what that does and does not mean, because the difference is the whole point of the project.

The three levels, and why they are not the same

Measured

A recording of that model shows the behaviour, frame by frame. These are the only capabilities with a write path.

Inferred

Read out of the vendor app's own constants, and not yet confirmed against hardware. Useful as a map, not as a permission slip.

Unconfirmed

Plausible from the protocol's shape and nothing more. Shown as a reading when the device reports it; never written to.

A capability marked writable: true must be measured, and the registry enforces that: a profile claiming a write path on inferred evidence fails to load, and the app says why instead of starting with a control that might not work.

What this page will not do is list model names as supported. The protocol is shared across the family, which is why a read-only connection is a reasonable expectation — but a list of forty model numbers that nobody has recorded would be a claim the project cannot stand behind, and it would be the same overreach this app exists to avoid. If your model connects and reads, the app will tell you what it found. That is a real answer; a model-name list would not be.

If yours says "read-only" and you want it writable, the next section is the whole recipe, and it takes about twenty minutes.

Adding a model

  1. Record it. Run the app with tracing enabled so every frame in both directions is written out as hex, then change one setting at a time, slowly, and note what you changed. A recording without a note is only half the evidence.
  2. Freeze it into the corpus. The recording becomes captures/<id>/frames.hex with a capture.json carrying its provenance: model, firmware string, date, tool and channel. The Swift corpus is generated from that file, and a test asserts the two agree, so a fixture cannot be edited out of step with its provenance.
  3. Write the profile. One JSON file in devices/. Each capability gets read, writable and a confidence, and the confidence has to cite its evidence — a capture for measured, a class and method in the vendor app for inferred, and nothing at all for unconfirmed.
  4. Run the tests. swift test replays the corpus through the real session and checks the state it lands in; the registry has its own rules and refuses profiles that break them.
  5. Open a pull request. Model, firmware string, what you set, what came back.

Nothing in that list involves touching the Swift, which is the point of the registry being a file rather than a set of model checks in the source. A model nobody has catalogued still connects, still reads, and simply draws no controls that could lie.

What the registry refuses

The registry is not documentation, it is enforced. A profile that breaks any of these does not load, and the app prints the reason:

  • A capability key that is not in the vocabulary.
  • A value the protocol does not have, or values where none belong and none where one does.
  • measured citing anything other than a capture or a hardware loop-back.
  • inferred not citing the vendor app, or unconfirmed citing anything at all.
  • writable: true on anything that is not measured.
  • Two fallback profiles, or none.

The rules were verified by breaking the shipped profile deliberately and confirming each one produced the named error, rather than by reading the code and assuming.

Questions

Will BudsDesk work with my OPPO Enco, OnePlus Buds or realme Buds?
If your model advertises the vendor's control service, BudsDesk will connect and show everything it reports: battery where per-bud data exists, wear state, the active noise-control mode, the equalizer preset, the codec and the firmware string. It will not write any setting until that exact model has been recorded, because writing a value nobody has observed on your model risks putting it in a state the app cannot explain.
How does a model become fully supported?
Somebody records it. Run the app with tracing on, set each control in turn while the traffic is captured, and commit the recording with its provenance: model, firmware string, date and tool. Then add one JSON file to devices/ describing what that recording shows, with each capability marked measured, inferred or unconfirmed and citing its evidence. No compiler change is involved.
Why not just enable the controls for every model in the family?
Because a setting that is written and not understood can leave the earbuds in a state the app cannot describe or undo. The app offers exactly what has been observed to work on that model. That restraint is the product: an app that says it changed something and did not is worse than an app with fewer buttons.

Related work worth knowing

This is not the first project to notice that these earbuds deserve a desktop client. If yours is not a BudsDesk model, one of these may be exactly what you need, and all of them are somebody's unpaid work:

  • Realme TWS Mac Controller — a macOS client for realme earbuds, MIT licensed, and independently documented the same thing this project did: that macOS exposes no control at all.
  • GalaxyBudsClient and nothing-x-macos — the same idea for Samsung and Nothing, and both worth reading if you want to see how far a reverse-engineered companion client can go.
  • FreeBuddy — the same problem for Huawei FreeBuds.

Different protocols, different vendors, same missing piece. None of them shares code with BudsDesk.

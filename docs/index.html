Control your earbuds from your Mac

The earbuds came with a phone app. On a Mac they are a Bluetooth audio device and nothing more. BudsDesk opens the control channel the phone app uses, so noise control, the equalizer, BassWave, touch gestures and per-bud battery all work from the Mac.

Download for macOS Read the source

Free and MIT licensed. macOS 26 or later on Apple silicon. Not on the Mac App Store. Latest release v0.1.2 — what changed.

What it does

Every control below writes to the earbuds and then reads the answer back. Nothing is drawn that the hardware has not been seen to accept.

  • Noise control

    Off, Noise Cancellation at High, Moderate, Low or Auto, Transparency and Adaptive, the same set the phone app offers, switched from the window or the menu bar.

  • Equalizer and BassWave

    Preset switching, including the custom slot when the earbuds report one, and BassWave over the range the device itself reports rather than a guessed one.

  • Touch gestures

    Double tap, triple tap, touch and hold and slide, limited to the actions this hardware has actually been observed to store.

  • Battery and wear

    Left and right read separately and never averaged, plus which bud is in your ear and which is in the case, in the window and in the menu bar.

  • Details worth seeing

    The active audio codec, the firmware version string verbatim, and the multi-connect list with each device's connection state.

  • A command line too

    The same binary replays a capture, prints the capability registry and runs the protocol self-check, so every part can be inspected without a window.

What it will not do

The list is short because the app is arranged around it. Every one of these is a decision, not an omission.

  • It will not touch firmware. Updates live on a separate service, and the app never opens it: not for discovery, not for testing. A failed firmware write turns earbuds into a brick, and nothing here is worth that.
  • It will not guess. No command id is sent that has not been seen in a recording, and no frame is fuzzed to find out.
  • It will not write a setting the hardware has not been seen to accept. An unconfirmed capability has no write path at all, and its control is drawn disabled with the reason on it.
  • It will not talk to the network. No accounts, no telemetry, no analytics, no update checks. It speaks to the earbuds and to nothing else, and behaves the same with the network down.
  • It will not claim the case's battery. The earbuds do not report it on this channel, so the app says so instead of drawing an empty cell.

The case's charge is a missing report, not a missing feature. Across a whole recording session every battery reply carried exactly two slots, left and right, even while the wear reply named the case on every poll. Whatever path the case's charge takes to the phone app, this channel is not it.

Installing it

  1. Download the disk image.

    Drag BudsDesk into Applications.

  2. Pair the earbuds.

    In System Settings, Bluetooth, if they are not paired already. They connect as audio devices without BudsDesk.

  3. Open BudsDesk.

    Allow Bluetooth access when macOS asks. The permission belongs to the app, so it survives updates.

Or build it

git clone https://github.com/shashank99928/BudsDesk
cd BudsDesk
swift test        # corpus replay, total parsers, registry and session
./build.sh        # assembles BudsDesk.app, checks symbols, runs the self-check

Requires macOS 26+, Apple silicon and Swift 6.2. The build is ad-hoc signed rather than notarised, so the first launch asks you to confirm opening it: right-click the app and choose Open, or allow it in System Settings, Privacy & Security. That is what an app distributed outside the App Store looks like without a paid developer account, and saying so is better than pretending otherwise.

Questions

Can I change noise cancelling on these earbuds from a Mac?
Not through macOS. Its Bluetooth settings connect and disconnect the earbuds and nothing more, because the noise-control and equalizer settings live on a separate vendor control channel that no Apple software opens. BudsDesk opens that channel, which is why it can change the mode from the Mac. Pairing still happens in System Settings, and the earbuds connect as audio devices without it.
Do I still need the phone app?
For firmware updates, yes. For daily use — noise mode, equalizer, BassWave, gestures — no. Those settings are stored on the earbuds, so a change made here shows up on the phone and the other way round.
Does BudsDesk replace the HeyMelody app on the Mac?
It is not a port of it and shares none of its code: it was written separately by recording what the earbuds' own control channel carries. It covers the settings that were measured on this channel, and it deliberately does not do firmware updates. See the honest comparison.
Which earbuds models are supported?
One model is verified end to end against hardware: the OnePlus Buds 4. Any other OPPO, OnePlus or realme model that advertises the same control service will connect and show everything it reports, but with no write path, because writing a setting that has not been observed to work on that model would be a guess. Adding a model means recording it and adding one JSON file.
Why does only one model write settings?
Because only one model has been recorded. The protocol is shared across the family, which is why other models connect and read, but a setting is only enabled once it has been observed to work on that model. Guessing is how an app starts lying.
Is the charging case's battery shown?
No, because the earbuds never report it on this channel. Across a full recording session every battery reply carried exactly two slots, left and right, even while the wear reply named the case. BudsDesk says "the case is present but has not reported a charge — on this channel it never does" rather than drawing an empty cell.
Does BudsDesk update the earbuds' firmware?
No, and it never will. Firmware updates live on a separate service that is never opened by this app — not for discovery, not for testing. A failed firmware write bricks hardware, and the payoff does not justify the risk.
Does it send anything to a server?
No. No accounts, no telemetry, no analytics and no update checks. It is not sandboxed but makes no network calls, and it can be run with the network down and behaves identically. The source is public, so this is checkable rather than promised.
Is it free, and is it on the App Store?
It is MIT licensed and free: no account, no paid tier, no in-app purchase. It is not on the Mac App Store. It ships as a disk image from GitHub Releases and is ad-hoc signed, so the first launch asks you to confirm opening it.

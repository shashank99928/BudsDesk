Control your OPPO, OnePlus or realme earbuds from your Mac

The earbuds came with a phone app. On a Mac they are a Bluetooth audio device and nothing more — no noise cancelling control, no equalizer, no gesture remapping, and a single merged battery icon at best. BudsDesk is the missing desktop app.

Download for macOS Read the source

Free, MIT licensed. macOS 26 or later on Apple silicon. Not on the Mac App Store.

What “verified” means here. Every byte the app sends was first seen in a recording of real hardware, and every feature is labelled measured (a recording shows it), inferred (read out of the vendor's own app constants, not yet confirmed) or unconfirmed (plausible, nothing observed). A feature that is not measured has no write path in the app at all. That is a design decision, not a caveat.

What it does

On the one model measured end to end, the OnePlus Buds 4:

Noise control

Off, Noise Cancellation at High, Moderate, Low or Auto, Transparency, and Adaptive — the same set the phone app offers, switchable from the menu bar or the window.

Equalizer & BassWave

Preset switching including the custom slot when one is saved on the earbuds, and BassWave over the range the device itself reports rather than a guessed one.

Touch gestures

Remap double tap, triple tap, touch and hold, and slide — limited to the actions the hardware has actually been observed to store.

Battery & wear

Left and right read separately, never averaged, plus which bud is in your ear and which is in the case. Shown in the menu bar as well as the window.

Details worth seeing

The active audio codec, the firmware version string verbatim, and the multi-connect device list with each device's connection state.

A command line, too

The same binary replays a capture, prints the capability registry, and runs the protocol self-check — so the parts can be inspected without a window.

Every control is gated by a capability registry (devices/*.json) rather than by model-name branches in the code. A model nobody has catalogue yet still connects, still shows everything it reports, and simply has no write path — the app tells you that instead of pretending.

What it will not do

  • It will not touch firmware. Updates live on a separate service, and the app never opens it — not for discovery, not for testing. Firmware updates are out of scope permanently. A failed firmware write turns earbuds into a brick; nothing here is worth that.
  • It will not guess. No fuzzing, no enumerating command ids, no sending a frame that was not first seen from the hardware.
  • It will not write a setting the hardware has not been seen to accept. An unconfirmed capability has no write path.
  • It will not touch the network. No accounts, no telemetry, no analytics, no update checks. It speaks to the earbuds and to nothing else.
  • It will not claim the case's battery. See below — the earbuds do not report it on this channel, so the app says so rather than drawing an empty cell.

Case battery is a missing report, not a missing feature. Across a whole recording session every battery reply carried exactly two slots — left and right — even while the wear reply named the case on every single poll. Whatever path the case's charge takes to the phone app, this channel is not it.

Install

  1. Download the disk image and drag BudsDesk into Applications.
  2. Pair the earbuds with the Mac in System Settings → Bluetooth if they are not already paired. They connect as audio devices without BudsDesk.
  3. Open BudsDesk and allow Bluetooth access when macOS asks. The permission is tied to the app's bundle identifier, so it survives updates.

The build is ad-hoc signed, not notarised, so the first launch needs a confirmation: right-click the app and choose Open, or allow it in System Settings → Privacy & Security. This is what an app distributed outside the App Store looks like without a paid developer account; saying so is better than pretending otherwise.

Or build it

git clone https://github.com/shashank99928/BudsDesk
cd BudsDesk
swift test        # corpus replay, total parsers, registry and session tests
./build.sh        # assembles BudsDesk.app, checks symbols, runs the self-check

Requires macOS 26+, Apple silicon and Swift 6.2. The app bundle carries its own capability registry, and the build verifies the bundled copy loads — a registry that is valid on disk and missing inside the app fails the build.

Questions people actually ask

Can I change noise cancelling on these earbuds from a Mac?
Not through macOS. Its Bluetooth settings connect and disconnect the earbuds and nothing more, because the noise-control and equalizer settings live on a separate vendor control channel that no Apple software opens. BudsDesk opens that channel, which is why it can change the mode from the Mac. Pairing still happens in System Settings, and the earbuds connect as audio devices without it.
Do I still need the phone app?
For firmware updates, yes. For daily use — noise mode, equalizer, BassWave, gestures — no. Those settings are stored on the earbuds, so a change made here shows up on the phone and the other way round.
Does BudsDesk replace the HeyMelody app on the Mac?
It is not a port of it and shares none of its code: it was written separately by recording what the earbuds' own control channel carries. It covers the settings that were measured on this channel, and it deliberately does not do firmware updates. See the honest comparison.
Which earbuds models are supported?
One model is verified end to end against hardware: the OnePlus Buds 4. Any other OPPO, OnePlus or realme model that advertises the same control service will connect and show everything it reports, but with no write path, because writing a setting that has not been observed to work on that model would be a guess. Adding a model means recording it and adding one JSON file.
Why does only one model write settings?
Because only one model has been recorded. The protocol is shared across the family, which is why other models connect and read, but a setting is only enabled once it has been observed working on that model. Guessing is how an app starts lying.
Is the charging case's battery shown?
No, because the earbuds never report it on this channel. Across a full recording session every battery reply carried exactly two slots, left and right, even while the wear reply named the case. BudsDesk says "the case is present but has not reported a charge — on this channel it never does" rather than drawing an empty cell.
Does BudsDesk update the earbuds' firmware?
No, and it never will. Firmware updates live on a separate service that is never opened by this app — not for discovery, not for testing. A failed firmware write bricks hardware, and the payoff does not justify the risk.
Does it send anything to a server?
No. No accounts, no telemetry, no analytics and no update checks. It is not sandboxed but makes no network calls, and it can be run with the network down and behaves identically. The source is public, so this is checkable rather than promised.
Is it free, and is it on the App Store?
It is MIT licensed and free: no account, no paid tier, no in-app purchase. It is not on the Mac App Store. It ships as a disk image from GitHub Releases and is ad-hoc signed, so the first launch asks you to confirm opening it.

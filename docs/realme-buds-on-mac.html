realme Buds on your Mac

realme Buds speak the same vendor control channel as OPPO and OnePlus earbuds, so a realme connection behaves the same way: it connects, it reports its state, and it stays read-only until somebody records a realme model. Nobody has, for this project — and the most useful thing this page can do besides say so is point you at the independent realme Mac client that exists.

One protocol, three brand names

The earbuds OPPO, OnePlus and realme sell are separate products, but the serial service they use for settings is the same one. On the hardware measured here it is named enco link and published under the UUID 0000079a-d102-11e1-9b23-00025b00a5a5. A realme earbud that publishes that same service is answering the same protocol, whichever name is on the box.

realme models also show that the family is not perfectly uniform underneath. A second serial channel named Realme Pearl has been seen in the SDP record on some models, next to the channel the measured unit uses. That is exactly why BudsDesk asks the device which channel the service is on instead of assuming a number: a model that puts the service somewhere else stays reachable, and no firmware service is ever opened on the way — the OTA channel is closed to this app permanently.

What a realme connection reads today

A realme model that advertises the control service gets a session. What it shows is what the earbuds report, and nothing is written:

  • Battery — per bud where the earbuds report it, left and right never merged. A model that does not report a figure shows as not having reported, not as 0%.
  • Wear state — which bud is in your ear and whether the case is closed.
  • Noise mode and equalizer preset — the current values, as the earbuds tell them, with the controls to change them drawn disabled and the reason printed on the card.
  • Codec and firmware string — the codec the link negotiated, and the firmware string printed verbatim rather than tidied into a format that could hide a mismatch.

Read-only means read-only. No setting on a realme model has been observed to be accepted, so no control is enabled — the window's footer says Verified write paths: none. Hidden controls would look like a smaller app; disabled ones with the reason on them tell you the truth about the evidence behind them.

Another realme Mac app exists

This is not the only attempt, and a realme owner should know that before deciding anything. Realme TWS Mac Controller is an independent, MIT-licensed macOS client for realme earbuds, and it documented the same absence this project did: macOS exposes no control over these settings at all. It shares no code with BudsDesk.

Two projects working on the same problem is not a problem. If one of them supports your model and the other does not, use the one that does — and if you record your model for this project, you have made the next person's afternoon shorter.

How a realme model becomes writable

Somebody records it. Turn tracing on, change one setting at a time while every frame in both directions is written out as hex, and commit the recording with its provenance: model, firmware string, date, tool and channel. Then add one JSON file to devices/ describing what that recording shows — each capability marked measured, inferred or unconfirmed, with its evidence cited. No Swift is touched, and it takes about twenty minutes.

The supported-models page has the full recipe and the rules the registry enforces, including the one that decides whether a control gets a write path at all: writable: true on anything that is not measured fails to load.

Questions

Does BudsDesk work with realme Buds Air 5 Pro?
If it advertises the vendor's control service, it will connect and read: battery per bud where the earbuds report it, wear state, the active noise mode, the equalizer preset, the codec and the firmware string. It will not change any setting, because no realme model has been recorded in this project yet — a write path only exists where a recording of that model does. If the earbuds do not publish the service, nothing is sent at all.
What is the "Realme Pearl" channel?
A second Bluetooth serial channel that has been seen in the SDP record on some realme models, alongside the one the measured unit uses for the vendor's control service. It is why BudsDesk resolves the channel number from the device's own SDP record at runtime instead of hard-coding one: a model that names or numbers its channels differently is still reachable. The firmware OTA channel is a separate thing again, and it is never opened.
Is there another Mac app for realme earbuds?
Yes. Realme TWS Mac Controller is an independent, MIT-licensed macOS client for realme earbuds, and it reached the same conclusion about macOS that this project did. It is somebody else's free work, it shares no code with BudsDesk, and if it supports your model, use it.
Which realme models are measured by BudsDesk?
None yet, and the site says so rather than listing model names as supported. One model is measured end to end across the whole family, the OnePlus Buds 4; every other OPPO, OnePlus and realme model connects and reads under the same rules. Naming forty models as "supported" would be the kind of claim this project exists to avoid.
